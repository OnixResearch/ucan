# Verified Boundaries

Production-readiness labels for these boundaries are governed by `docs/production-readiness.md` and `docs/production-readiness.json`. Current verified bridge coverage supports a controlled integration surface, not built-in production platform behavior.

This document records the current verified-logic bridge boundaries after the UCAN audit OpenSpec drain. "Verified" means routed through the vendored `verified-logic` primitives; ordinary Rust shell orchestration remains tested and bounded, but not formally verified in this crate. `docs/verified-bridge-coverage.md` is the guard-readable inventory that classifies each public verified export and vendored UCAN/WOT module as `live-path`, `public-helper`, `candidate`, or `documented-boundary`.

## Newly exposed exact bridge seams

- `typed_caveat_is_satisfied` and `typed_caveat_set_is_satisfied` expose the vendored finite typed caveat predicates for `VerifiedWebOfTrustCaveat::{TimeBound, RateLimit}` with explicit `VerifiedWebOfTrustCaveatContext`. `typed_caveat_ascii_decimal_payload_is_valid` and `typed_caveat_rate_limit_payload_shape_is_valid` route supported typed-caveat payload byte-shape admission through vendored `ucan_caveat` helpers before runtime UTF-8/u64 parsing. `VerifiedTypedCaveatPolicySet` is the first-party shell adapter for the same exact subset, recognizing only `time/before/unix` ASCII-decimal not-after payloads and `rate/limit/window` ASCII-decimal `max_count:window_seconds` payloads before delegating satisfaction to the verified predicate. UTF-8/decimal parser correctness, overflow semantics, clock/counter provenance, arbitrary caveat policy truth, and token provenance remain shell or caller boundaries.
- `web_of_trust_attestation_payload_bytes`, `web_of_trust_attestation_signature_is_valid`, and `web_of_trust_attestation_is_active_at` expose deterministic public WOT attestation evidence helpers.
- `web_of_trust_revocation_payload_bytes`, `web_of_trust_revocation_signature_is_valid`, `web_of_trust_revocation_matches_attestation`, and `web_of_trust_revocation_is_effective_at` expose deterministic public WOT revocation evidence helpers.
- `web_of_trust_threshold_accepts` exposes the finite WOT threshold policy predicate over caller-supplied roots, attestations, revocations, subject digest, threshold, depth, and explicit time.
- `compact_token_split_is_valid` exposes the vendored compact-token split admission predicate over already-split encoded header, payload, and signature bytes, rejecting embedded compact separators and checking that compact bytes equal `header.payload.signature`. The shell uses it in `parse_compact_token` immediately after ordinary Rust string splitting.
- `compact_token_envelope_is_valid` exposes the vendored compact-token framing predicate over already-encoded header, payload, signature, compact-token, and signing-input bytes. The shell uses it in `parse_compact_token` after compact split admission and before base64url/JSON/signature decoding.
- `base64url_segment_is_valid` exposes the vendored base64url-no-pad segment admission predicate over encoded segment bytes. The shell uses it in `decode_part` before runtime decoding to reject non-URL-safe/padded bytes and impossible unpadded length class `len % 4 == 1`; the actual decoded bytes remain a runtime codec boundary.
- `json_object_bytes_are_valid` exposes the vendored decoded JSON object byte-envelope admission predicate over decoded bytes plus explicit first/last significant byte indexes for advanced callers. The live compact-token shell uses `verified_json_object_bytes` to route first/last significant-byte discovery and object-envelope admission through vendored `verified-logic` for compact header and payload bytes after base64url decoding and before serde parsing; serde parser correctness, canonicalization, duplicate-key behavior, and decoded-byte correctness remain runtime boundaries.
- `parsed_header_is_valid` exposes the vendored parsed-header admission predicate over serde/shell-supplied parsed `alg` and `typ` bytes. The shell uses it in structural token validation to accept only exact `EdDSA` / `JWT` bytes after JSON parsing; JSON parser correctness, UTF-8/string handling, duplicate-key behavior, canonicalization, decoded-byte provenance, signing-input provenance, and cryptographic correctness remain runtime boundaries.
- `signer_algorithm_is_valid` exposes the same vendored supported-algorithm byte admission predicate for signer-reported algorithm strings. The signer-based issuance path uses it before accepting a `TokenSigner`; signer honesty, signer I/O, key provenance, public-key derivation, signing, and cryptographic verification remain runtime boundaries.
- `parsed_claims_presence_is_valid` exposes the vendored parsed-claims presence predicate over serde/shell-supplied issuer, audience, attenuations, proof-list, expiration, and not-before field-presence booleans. The shell uses it in `validate_decoded_token` before constructing core claim input; serde parser correctness, duplicate-key behavior, field extraction truth, string validation, capability parsing, proof-reference decoding, temporal values, signing-input provenance, cryptography, and token provenance remain runtime boundaries.
- `parsed_did_claims_are_valid` exposes the vendored parsed DID claim admission predicate over serde/shell-supplied issuer/audience presence, non-empty, and trimmed booleans. The shell uses it after required-claims presence admission and before core claim construction; JSON parser correctness, string extraction truth, duplicate-key behavior, DID syntax/method semantics, key resolution, signing-input provenance, cryptography, and token provenance remain runtime boundaries.
- `parsed_temporal_order_is_valid` exposes the vendored parsed temporal-order predicate over serde/shell-supplied numeric `nbf` and `exp` values. The shell uses it after required-claims presence admission and before core claim construction to require `nbf < exp`; JSON parser correctness, numeric deserialization correctness, duplicate-key behavior, wall-clock freshness, clock-source correctness, expiration-at-now policy, proof/backend truth, cryptography, and token provenance remain runtime or caller-supplied boundaries.
- `parsed_proof_reference_list_shape_is_valid` and `proof_reference_collection_is_valid` expose vendored finite proof-reference list/collection admission over shell-supplied encoded-entry, decoded-entry, non-empty, and count-bound facts. The shell uses them before proof-reference input construction and before proof-store lookup; base64 decoder correctness, BLAKE3 correctness, reference semantic truth, proof truth, duplicate semantic policy beyond supplied facts, and backend provenance remain runtime or caller-supplied boundaries.
- `parsed_capability_list_shape_is_valid` and `parsed_caveat_list_shape_is_valid` expose vendored finite parsed capability/caveat list-shape predicates over serde/shell-supplied field-presence facts. The shell uses them before core capability/caveat construction; JSON parser correctness, string validation, ability/resource semantics beyond existing verified capability admission, caveat identifier construction provenance, opaque payload meaning, and policy truth remain runtime boundaries.
- `VerifiedCapability::{has_wildcard_segment,is_concrete}` now route ability wildcard-segment discovery/concrete-admission through vendored `verified_logic::ucan_ability`. This verifies only finite segment equality against full `*` path segments after core capability parsing; capability string parsing, resource semantics, and higher-level authorization policy remain separate boundaries.
- `parsed_caveat_payloads_are_valid` exposes vendored finite parsed caveat payload admission over shell-supplied payload presence, encoded non-empty, base64url-no-pad structural admission, and decoded non-empty facts. The shell derives these facts while converting decoded caveat payloads before core caveat construction; base64url decoded-byte correctness, payload parser correctness, typed caveat semantics, clocks, counters, policy truth, and token provenance remain runtime or caller-supplied boundaries.
- `proof_store_result_is_valid` and `revocation_check_is_valid` expose vendored result-transcript predicates for caller-injected proof-store and revocation backend responses. The shell routes successful proof-load and revocation results through these bridges and remains fail-closed on backend errors or revoked facts; backend honesty, freshness, storage/network behavior, proof material provenance, and registry truth remain caller-supplied boundaries.
- `replay_admission_transcript_outcome`, `replay_admission_transcript_accepts`, and `replay_admission_transcript_first_failed_outcome` expose the vendored replay-admission transcript predicate over shell/caller-supplied allowed, duplicate, stale, malformed, denied, backend, or unknown outcome facts. `verify_invocation_with_replay` routes replay outcomes through this bridge before preserving an already-authorized invocation result or returning a fail-closed replay denial; nonce uniqueness truth, request identity provenance, durable replay storage, crash consistency, backend freshness, parser behavior, consumer envelope semantics, and clock correctness remain caller-owned boundaries.
- `signing_input_byte_provenance_is_valid` exposes exact `header.payload` byte reconstruction over already-encoded compact parts. The shell uses it immediately after compact-token splitting to check signature input bytes before envelope admission; encoded-part provenance, JSON canonicalization, base64 decoding, and Ed25519 correctness remain runtime/crypto boundaries.
- `caveat_preservation_is_valid` exposes the vendored opaque caveat identifier preservation predicate over shell-supplied parent and child caveat identifier byte vectors. The shell uses it during capability attenuation after verified resource/ability containment to require each parent caveat identifier to appear exactly in the child caveat identifier set; caveat-document validation, length-prefix encoding provenance/injectivity, payload parsing, caveat policy semantics, clocks, counters, backend truth, token provenance, and cryptographic correctness remain runtime or caller-supplied boundaries.
- `proof_reference_digest_is_valid` exposes the vendored proof-reference digest admission predicate over shell-computed digest bytes and candidate proof-reference bytes. It accepts only the fixed BLAKE3 digest width and exact reference/digest byte equality. The shell calls it in proof-reference construction immediately after runtime BLAKE3 hashing.
- `validate_secret_key_length`, `validate_public_key_length`, and `validate_signature_length` route Ed25519 byte-length admission through vendored `ucan_signature::{secret_key_len_is_valid,public_key_len_is_valid,signature_len_is_valid}` before typed verified key/signature construction. This verifies only fixed-width admission and preserves crypto/provenance/DID/parser non-claims.
- `verification_stage_transcript_outcome` exposes the vendored finite verification-stage transcript predicate over caller/shell-supplied booleans for parse, structural, key-resolution, signature, envelope, revocation, proof-load, proof-chain, and authorization stage facts. It accepts exactly when every stage is true and reports the first failed stage in fixed order without carrying token bytes or backend payloads.
- `backend_transcript_accepts` and `backend_transcript_first_failed_operation` expose the vendored finite backend-operation transcript predicate over shell-supplied `KeyResolution`, `ProofLoad`, and `Revocation` success facts. The live verifier records these operation facts around caller-injected resolver/proof-store/revocation calls, validates successful top-level transcripts, and returns fail-closed backend errors when a backend reports failure.
- `proof_traversal_transcript_is_valid` exposes the vendored finite proof traversal transcript predicate over already-resolved entries, visited proof-reference bytes, explicit budgets, target operation, time, and supplied revocation facts.
- `proof_traversal_dag_transcript_is_valid` exposes the vendored finite multi-parent proof DAG transcript predicate over already-resolved entries, topological parent indices, visited proof-reference bytes, explicit budgets, target operation, time, and supplied revocation facts.
- `invocation_request_is_authorized`, `receipt_execution_is_valid`, and `invocation_chain_is_authorized` expose vendored finite invocation/receipt/chain helpers over caller-supplied authorization, receipt, proof-reference, and revocation facts; they do not perform proof fetching, compact-token verification, cryptography, DID/key lookup, revocation-backend queries, caveat-policy evaluation, persistence, replay protection, or ambient clock reads.
- `revocation_reference_is_listed`, `structural_chain_is_valid`, and `structural_chain_not_revoked_is_valid` expose vendored finite revocation-reference and structural-chain helpers over caller-supplied proof references, chain entries, and revocation facts; they do not prove backend truth, freshness, proof material provenance, parser behavior, cryptography, or runtime traversal orchestration.
- `web_of_trust_principal_digest`, `web_of_trust_principal_digest_is_valid`, and `web_of_trust_ucan_authorization` expose vendored finite WOT principal digest/admission and UCAN authorizer helpers over caller-supplied root/trust/caveat/revocation/identity facts; they do not perform DID/CID decoding, compact-token verification, cryptographic verification, proof fetching, key lookup, revocation-backend checks, trust-store discovery, caveat policy evaluation, storage/network access, persistence, replay protection, or ambient clock reads.

These helpers do not fetch evidence, resolve DIDs, sign, persist data, consult registries, provide replay protection, install default caveat policies, or read ambient clocks.
- The `verified-proof-traversal-orchestration`, `verified-compact-token-codec-structure`, `verified-core-structural-validators`, `verified-ability-helper-predicates`, and `verified-backend-transcript-aggregation` readiness surfaces summarize existing live-path bridges; they remain finite structural/transcript claims and do not promote parser, codec, crypto, backend, storage, or consumer-policy truth into verified logic.

## Shell-local boundaries retained intentionally

- Compact-token string splitting remains ordinary Rust, but the shell now routes split admission through `compact_token_split_is_valid`, which verifies separator-free already-split encoded parts and exact `header.payload.signature` reconstruction. Base64url segment alphabet/length structural admission now routes through `base64url_segment_is_valid`; decoded header/payload significant-byte index discovery and object-envelope admission route through `verified_json_object_bytes` / `json_object_bytes_are_valid`; parsed header field admission routes through `parsed_header_is_valid`; parsed claims-presence, temporal-order, proof-reference list-shape, proof-reference collection, parsed capability/caveat list-shape, parsed caveat payload admission, proof-store result, revocation result, and signing-input provenance admission route through their vendored bridges; but base64url decoded-byte correctness, JSON parser correctness/canonicalization beyond admitted `alg`/`typ` bytes and admitted required-claim/`nbf < exp` facts, wall-clock freshness, clock-source correctness, BLAKE3 proof-reference derivation, and Ed25519 runtime crypto remain trusted runtime boundaries. The shell also routes signing-input framing through `compact_token_envelope_is_valid`; proof-reference construction routes shell-computed digest/reference byte admission through `proof_reference_digest_is_valid`. These bridges do not verify base64url decoded-byte correctness, JSON parser correctness, canonicalization beyond admitted `alg`/`typ` bytes, duplicate-key handling, BLAKE3 correctness, hash input provenance, or signature internals. `verification_stage_transcript_outcome` can verify caller/shell-supplied stage admission and first-failure ordering, and `backend_transcript_accepts` can verify finite backend-operation success/failure ordering, but neither verifies the truth, freshness, provenance, availability, or security of any parser, cryptographic operation, resolver, proof-store, revocation backend, proof-chain, authorization, or caveat-policy fact. `VerifiedTypedCaveatPolicySet` verifies satisfaction only after the shell parses documented typed caveat payload bytes and callers supply time/count facts; payload parsing, clock choice, quota accounting, freshness, and provenance remain trusted shell inputs. The shell has focused regressions for malformed shape, invalid base64/JSON, signing-input stability, proof-reference stability, backend fail-closed errors, typed caveat policy admission/denial, and redacted output.
- Live recursive proof traversal remains ordinary Rust orchestration. The current shell preserves caller-injected `KeyResolver`, `ProofStore`, and `RevocationChecker`, bounded proof depth/count/input bytes, cycle rejection, fail-closed backend errors, proof-link verification through `proof_link_is_valid`, proof-depth admission through `proof_depth_within_budget` / vendored `check_proof_hop_depth_budget` for hop-to-chain-length conversion and overflow rejection, and structural/helper bridges for callers with already-resolved finite chains, linear traversal transcripts, or topologically ordered multi-parent DAG transcripts. The verified traversal transcript bridge checks finite resolved-data consistency, and the live shell emits/checks DAG transcripts for no-proof tokens, single-parent linear proof chains, and representable multi-parent proof graphs whose resource, caveat-preservation, and exact or wildcard-segment ability attenuation are accepted by the vendored predicate. It still does not model the live resolver/proof-store state machine, backend freshness, compact-token parsing, signature byte verification, proof-reference hashing, revocation backend correctness, or recursive runtime orchestration outside caller/shell-supplied transcripts.
- Invocation replay/nonce admission remains ordinary Rust orchestration through caller-injected `ReplayAdmission`. `verify_invocation_with_replay` first performs compact-token verification plus caveat/policy authorization, then fails closed if the admission hook reports duplicate, stale, malformed, denied, or backend errors. Durable nonce stores, crash recovery, backend freshness, and consumer-specific envelope semantics remain outside verified-logic and outside this crate.
- Opaque shell caveat preservation now routes through `caveat_preservation_is_valid` for exact byte-identifier preservation. Shell construction of those identifiers from domain/type/key/payload length-prefixed components remains ordinary Rust and does not prove application caveat semantics or parser correctness.
- Shell caveat evaluation aggregation now routes through `caveat_evaluation_transcript_accepts` / `caveat_evaluation_first_failed_index`, verifying only finite fail-closed aggregation over shell-emitted `policy_present` and `satisfied` facts. Policy lookup truth, arbitrary policy correctness, typed payload parsing, clocks, counters, freshness, token provenance, and cryptography remain outside that claim.

## Implementation guidance

Future changes should only claim a shell behavior is verified when the public helper or internal path delegates the exact same predicate to `vendor/verified-logic`. If the available vendored primitive only covers a lower-level or typed subset, document it as an opt-in bridge and keep caller-injected shell boundaries explicit.
